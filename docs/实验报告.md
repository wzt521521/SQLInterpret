# 大型平台软件设计实习报告：MiniDBMS

> 项目：MiniDBMS / SQLInterpret  
> 日期：2026-09-14  
> 小组分工：zby—SQL 编译器；wzt—页式存储与缓存；wzy—数据库引擎、CLI 与总集成。  
> 报告依据：`docs/实验分工.md` 和课程任务摘要。提交前可按学校模板补充姓名、学号、指导教师与现场截图。

## 一、实践目的

通过实现一个简化数据库管理系统，理解 SQL 从文本解析、语义检查、逻辑计划到执行、数据页和磁盘文件的完整路径。重点掌握模块接口、Catalog 的唯一数据源作用、行页映射、缓存写回与重启恢复，以及如何在不同阶段报告可定位的错误。

## 二、实践内容

系统支持 `CREATE TABLE`、`INSERT`、`SELECT`（可带 `WHERE`）、`DELETE`（可带 `WHERE`）。列类型为 `INT` 和 `VARCHAR`；条件支持比较、算术、`AND`、`OR`、`NOT` 与括号。数据表结构、数据和删除标记通过 4096 字节页保存；程序正常关闭后再启动仍能查询。CLI 支持多条 SQL、错误后继续、缓存统计与淘汰日志。

三层职责如下：

| 模块 | 主要工作 | 对接点 |
| --- | --- | --- |
| SQL 编译器（zby） | Token、AST、语义检查、逻辑 Plan、常量折叠和布尔化简 | 只读 `CatalogView`，输出公共 `PlanNode` |
| 存储系统（wzt） | 固定页、文件分配位图、Buffer Pool、LRU/FIFO、刷新与统计 | 只暴露页号和 `bytes` 的 `StorageManager` |
| 数据库引擎（wzy） | 持久化 Catalog、行/页、六类 Plan、表达式、CLI、端到端联调 | 消费 Plan，并调用 `StorageManager` |

## 三、实践方法与设计

采用分层实现和自底向上验证。wzy 将逻辑页 0 固定为 Catalog 根页，根页指向 JSON 元数据快照链；更新时先写新快照并刷新，再切换根指针。表数据页使用 16 字节页头和 8 字节槽项，记录从页尾增长；DELETE 设置槽内 tombstone，扫描跳过已删除记录。`INT` 为小端有符号 64 位，`VARCHAR` 为长度前缀加 UTF-8 字节。

执行器只处理共享 `PlanNode`：`CreateTable` 写 Catalog，`Insert` 编码并写页，`SeqScan` 产生行，`Filter` 求值 WHERE，`Project` 按指定列顺序输出，`Delete` 通过行引用修改原槽。实际 SQL 仍由 zby 编译器解析；存储文件仍由 wzt 模块管理。详细格式和错误码见 [数据库引擎设计](database_engine_design.md)、[存储设计](storage_design.md)及[接口协议](api_contract.md)。

## 四、实践步骤

1. 同步已合并的 zby、wzt 模块，核对 `common/` 协议和编译器真实 Plan 结构。
2. 完成 Catalog 固定入口、元数据序列化、快照扩展和重启加载。
3. 完成 `RecordCodec`、槽式数据页、跨页插入、扫描与 tombstone 删除。
4. 完成表达式求值、六类 Plan 执行和单条 SQL 的基本失败清理。
5. 接通 CLI 与顺序编译执行，编写单元、端到端和跨进程重启测试。
6. 构建 C++ 原生编译器，运行全部测试与临时数据库演示。

## 五、实践结果

当前环境执行：

```text
python -m minidbms.sql_compiler.build_native    构建成功
python -m pytest tests/test_db.py -q            18 passed
python -m pytest -q                             118 passed
python examples/e2e_demo.py                     两个独立进程均成功
```

固定 SQL 演示首次 SELECT 得到 `(1, Alice)` 和 `(3, Carol)`；DELETE 影响 1 行；第二次 SELECT 与重新启动后的 SELECT 均得到 `(2, Bob, 17)` 和 `(3, Carol, 22)`。容量为 2 的缓存统计为读取请求 9、命中 7、未命中 2、淘汰 3、脏写 6。优化演示将 `TRUE AND age >= 10+8` 化简为 `age >= 18`。完整输出见 [端到端演示记录](e2e_demo_result.md)。

自动化测试覆盖 Catalog 跨页增长与损坏检测、INT/VARCHAR 边界、页槽删除、条件与短路求值、跨页扫描、失败插入清理、五阶段错误、CLI 错误后继续和两个进程间的持久化。测试使用临时目录，不覆盖人工演示数据库。

## 六、问题与解决过程

- **CREATE 后立即 INSERT 的 Catalog 时序：** 编译器不能预先假设新表存在。使用 `compile_and_execute`，逐条执行后让下一条语义分析读取正式 Catalog。
- **DELETE 经过 Filter 后如何找到原记录：** 扫描结果保留 `page_id + slot_id` 行引用，筛选不丢弃引用，删除时修改对应槽。
- **Catalog 大于一页：** 固定页 0 保存根指针，元数据快照拆成链式页并校验 CRC32。
- **缓存容量小于全表页数：** 顺序扫描可能每次都未命中，因此分别用跨页扫描验证淘汰、用热点页访问验证命中增长，不将两者混为同一断言。

## 七、实践结论

在当前实训基线内，四类 SQL 已经过“编译 → 逻辑 Plan → 执行 → 页式存储”完整链路，正常关闭后的表结构、数据和删除状态可恢复。原有 SQL 编译器和存储测试仍通过。项目不提供事务、WAL、并发控制或突然断电后的崩溃恢复；多行 DELETE 也不保证事务级全有或全无。

## 八、实践小结与 AI 辅助说明

实现中最关键的不是单独写出 SQL 或页读写，而是让 Catalog、Plan 和页号三种边界保持一致：编译器只读表结构，执行器决定行与页内容，存储层只处理页面字节。这样既能独立测试，也能在联调时定位错误所在阶段。
